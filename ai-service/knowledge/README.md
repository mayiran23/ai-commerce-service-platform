# 平台政策知识库（RAG 语料）

> 本目录是 AI 客服的「政策手册」。用户问"七天无理由怎么算""退货运费谁出"这类
> **没有工具可调、只能查规定**的问题时，AI 从这里检索原文，再照原文回答并标注出处。

---

## 一、为什么要单独维护这个目录

项目里的 AI 有两条知识来源，**职责必须分清**：

| 来源 | 回答什么 | 实现方式 | 举例 |
|---|---|---|---|
| **工具调用** | 某个人、某笔订单的**实际情况** | 调 Java `/internal/*` | "我这个订单还能退吗" → `check_refund_eligible` |
| **本知识库（RAG）** | 平台**规定是什么** | 向量检索 + 拼进提示词 | "七天无理由怎么算" → 检索 `01-*.md` |

🔴 **绝对不要**把"某订单能不能退"这类**要算的**问题写进语料。规则永远只有一处实现
（Java 的 `refund_deadline`），语料里再写一遍"签收后 7 天"只是**文字描述**，
不能代替计算。两边不一致时，AI 会同时给出矛盾答案。

---

## 二、文件命名规范

```
NN-主题.md          NN 是两位序号，决定文件顺序，从 01 开始
```

例：`01-seven-day-return.md`、`03-return-shipping-fee.md`

**为什么加序号**：① 检索结果里同分时按文件顺序稳定排序 ② 一眼看出主题覆盖全不全。

## 三、每篇文件的结构（必须照抄这个骨架）

```markdown
---
doc_id: POL-001
title: 七天无理由退货规则
category: 退货
effective_date: 2026-01-01
version: v1.0
---

# 七天无理由退货规则

## 1. 适用范围

（正文，200-500 字）

## 2. 起算时间

（正文，200-500 字）

## 3. 不适用情形

（正文，200-500 字）
```

### 3.1 front matter（文件最上面 `---` 包起来那段）

| 字段 | 说明 |
|---|---|
| `doc_id` | 唯一编号，格式 `POL-NNN`，全库不重复 |
| `title` | 中文标题，会显示在回答的"出处"里 |
| `category` | 分类：退货 / 物流 / 退款 / 发票 / 质量 / 会员 |
| `effective_date` | 生效日期。**政策会变，这个字段是防过期的** |
| `version` | 版本号，改一次加一档 |

### 3.2 标题层级（🔴 这是切分边界，最重要的一条）

**只用 `#`（文件标题）和 `##`（小节），不要用 `###`。**

原因：Day 2 的切块逻辑是**按 `##` 切**——一个 `##` 小节 = 一个检索单元。
用 `###` 会让一个小节被切得七零八落，检索出来只有半句话。

---

## 四、三条硬约束（违反任何一条，RAG 都会失效）

### 🔴 约束 1：退货起算点必须写「签收日」

代码里的规则是 `refund_deadline = 签收时间 + 7 天`（落在 `t_order_item.refund_deadline`）。

如果语料里写成"下单后 7 天"或"发货后 7 天"：

> 用户问"我上周签收的还能退吗" → 工具算出来 `eligible=true`
> → 语料检索出来说"发货后 7 天内" → **AI 同时给出两个矛盾结论**

这是 RAG 项目**最致命的失败模式**，比"检索不到"严重得多——检索不到只是不知道，
**检索错是自信地答错**。

### 🔴 约束 2：每小节必须自成一意

每个 `##` 小节被单独检索出来时，**必须不需要上下文就能读懂**。

禁止出现：
- ❌ "如上所述，运费由买方承担"（"如上所述"指的是哪段？检索不到）
- ❌ "详见第 3 节的处理流程"（检索单元里没有第 3 节）
- ❌ "除上述两种情形外"（"上述两种"是哪些？）

正确写法：把话写全。宁可重复，不要引用。

### 🔴 约束 3：单节 200-500 字，超 600 字就拆

切块太大 → 检索出来一整篇，无关内容稀释了关键信息，模型抓不住重点。
切块太小 → 一句话被切成两半，谁都读不懂。

**200-500 字是甜点区**：大约 3-6 句话，正好是一个完整的规则说明。

---

## 五、写作风格（写给人看，也给模型看）

- **用陈述句写"规定"，不要写"我们会尽力协助您"这种客服话术**。语料是"法条"，不是"回复模板"
- **数字要精确**：写"7 天"不写"一周左右"；写"买家承担"不写"一般由买家承担"
- **边界要明确**：写清"什么情况不适用"，比只写"什么情况适用"更有价值
- **不要写"根据某某法律"**：法律条款模型容易记错，写平台的**可执行规定**就好

## 七、🔴 一致性红线：语料必须和代码规则对上

写之前先记住这几条**代码里的硬规则**（`AfterSaleServiceImpl` / `check_refund_eligible`）：

| 规则 | 代码里的口径 | 语料里必须怎么写 |
|---|---|---|
| 退货期限 | 签收时间 + **7 天** | 「自**签收日**起 7 个自然日内」 |
| 前提条件 | 订单必须**已签收** | 「仅支持已签收订单申请」 |
| 未签收 | 返回 `NOT_RECEIVED` | 「运输途中不支持申请售后」 |
| 已取消 | 拒绝，文案"无需申请售后" | 「已取消订单无需申请售后」 |
| **超期** | `eligible=false` 但 `suggestManualReview=true` | 🔴 **「超过期限仍可提交，由人工审核」** |
| 置信度阈值 | < **0.7** 转人工 | （语料里**不写**——这是系统实现细节，不是政策） |

⚠️ 特别注意那条 **超期不是直接拒绝**——代码的设计是"转人工审核"。
语料里也必须这么写，否则 AI 会说"抱歉不能退"，而工具逻辑明明是"帮您转人工"。
